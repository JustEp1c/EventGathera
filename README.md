# EventGathera
Проектная работа, выполняемая в ходе прохождения курса "Продвинутая разработка на C# и .NET" от Яндекс.Практикум.

## Стек технологий

- .NET
- ASP.NET Core Web API
- Swagger

Перед запуском убедитесь, что установлены:

- .NET SDK 10
- IDE или редактор кода

## Инструкция для запуска проекта

1. Склонируйте репозиторий:

```bash
git clone https://github.com/JustEp1c/EventGathera.git
```
2. Перейдите в папку проекта:

```bash
cd EventGathera
```

3. Восстановите зависимости:

```bash
dotnet restore
```

4. Запустите приложение:

```bash
dotnet run --project .\src\EventGathera.Api\
```

После запуска в консоли будет отображён адрес приложения:

```bash
https://localhost:7153
http://localhost:5163
```

После запуска документация Swagger будет доступна в браузере по адресу:

```bash
https://localhost:7153/swagger
```

## Инструкция по запуску тестов

## Возможности

Приложение поддерживает базовые CRUD-операции:

- создание события
- получение списка событий
- получение события по идентификатору
- обновление события
- удаление события
- создание брони
- получение брони по идентификатору

### Фильтрация и пагинация событий

- **Фильтрация по названию** - поиск событий по частичному совпадению в названии (регистронезависимый)
- **Фильтрация по дате начала** - получение событий, начинающихся после указанной даты
- **Фильтрация по дате окончания** - получение событий, заканчивающихся до указанной даты
- **Комбинированная фильтрация** - одновременное применение нескольких фильтров
- **Пагинация** - разбивка результатов на страницы с настраиваемым размером

## Модели данных

### Event (Событие)

| Поле | Тип | Описание |
|------|-----|----------|
| Id | Guid | Уникальный идентификатор события |
| Title | string | Название события |
| Description | string | Описание события |
| StartAt | DateTime | Дата и время начала |
| EndAt | DateTime | Дата и время окончания |
| TotalSeats | int | Общее количество мест на событии |
| AvailableSeats | int | Текущее количество свободных мест|

### Booking (Бронь)

| Поле | Тип | Описание |
|------|-----|----------|
| Id | Guid | Уникальный идентификатор брони |
| EventId | Guid | ID события, на которое бронируют |
| Status | BookingStatus | Текущий статус брони |
| CreatedAt | DateTime | Дата и время создания брони |
| ProcessedAt | DateTime? | Дата и время обработки (для Confirmed/Rejected) |

### Статусы бронирования (BookingStatus)

| Статус | Значение | Описание |
|--------|----------|----------|
| Pending | 0 | Ожидает обработки (начальный статус) |
| Confirmed | 1 | Подтверждена (после успешной обработки) |
| Rejected | 2 | Отклонена (по различным причинам) |

## API Endpoints

### Бронирования (Bookings)

#### GET /bookings/{bookingId}

Получить бронь по ID.

**Пример запроса:**
```http
GET /bookings/987fcdeb-51a2-43d3-a456-426614174000
```
Пример ответа (200 OK):
```json
{
  "id": "987fcdeb-51a2-43d3-a456-426614174000",
  "eventId": "123e4567-e89b-12d3-a456-426614174000",
  "status": 1,
  "createdAt": "2026-04-14T10:30:00Z",
  "processedAt": "2026-04-14T10:30:05Z"
}
```

#### POST /events/{id}/book

Создать бронь на событие. Бронирование обрабатывается асинхронно в фоновом сервисе.

**Возможные статусы ответа:**
- `202 Accepted` - бронь успешно создана и ожидает обработки
- `404 Not Found` - событие с указанным ID не найдено
- `409 Conflict` - на событии нет свободных мест (овербукинг)

```http
POST /events/123e4567-e89b-12d3-a456-426614174000/book
```
Пример ответа (202 Accepted):
```json
{
  "id": "987fcdeb-51a2-43d3-a456-426614174000",
  "eventId": "123e4567-e89b-12d3-a456-426614174000",
  "status": 0
}
```

Пример ответа (409 Conflict):
```json
{
  "type": "https://tools.ietf.org/html/rfc9110#section-15.5.10",
  "title": "Conflict",
  "status": 409,
  "detail": "Нет свободных мест на это событие",
  "instance": "/events/123e4567-e89b-12d3-a456-426614174000/book"
}
```

## Фоновая обработка бронирований
### Как это работает

1. Создание брони: При POST запросе на /events/{id}/book создается бронь со статусом Pending

2. Фоновая обработка: BookingProcessingService (BackgroundService) запускается автоматически при старте приложения и работает в фоне:

* Каждые 2 секунды проверяет наличие новых броней

* Находит все брони со статусом Pending

* Обрабатывает каждую бронь (имитация обработки занимает 5 секунд)

* После успешной обработки меняет статус на Confirmed и устанавливает ProcessedAt

3. Получение статуса: Клиент может GET запросом на /api/bookings/{id} проверить текущий статус брони

```text
Клиент → POST /events/{id}/book → Бронь создана (Pending)
                                      ↓
                            BackgroundService (каждые 2 сек)
                                      ↓
                            Обработка брони (5 сек)
                                      ↓
                            Статус изменен на Confirmed
                                      ↓
Клиент ← GET /api/bookings/{id} ← Получен актуальный статус
```

## Синхронизация и потокобезопасность

Для обеспечения корректной работы в многопоточной среде используются следующие примитивы синхронизации:

1. lock в BookingService

```text
private readonly object _bookingLock = new object();

lock (_bookingLock)
{
    if (!foundEvent.TryReserveSeats())
    {
        throw new NoAvailableSeatsException("Нет свободных мест на это событие");
    }
    
    newBooking = new Booking { ... };
    _bookingStorage.Bookings.Add(newBooking);
}
```

Назначение: Обеспечивает атомарность операций при создании бронирования. Блокировка гарантирует, что:

* Проверка наличия мест и их резервирование происходят как единая неделимая операция

* Два параллельных запроса не смогут одновременно проверить наличие мест и создать бронирование, превышающее лимит

* Вставка нового бронирования в коллекцию происходит потокобезопасно

2. SemaphoreSlim в BookingProcessingService

```text
private readonly SemaphoreSlim _processingSemaphore = new(1, 1);

await _processingSemaphore.WaitAsync();
try
{
    // Обработка брони
    booking.Confirm();
}
finally
{
    _processingSemaphore.Release();
}
```

Назначение: Ограничивает количество одновременно обрабатываемых броней. Использование семафора гарантирует:

* Только один поток может обрабатывать бронь в каждый момент времени

* Предотвращает состояние гонки при изменении статуса брони и освобождении мест

## Сценарий с овербукингом

Рассмотрим ситуацию, когда на событие с 5 местами одновременно приходит 20 запросов на бронирование:

```text
Время 0: Событие имеет 5 свободных мест
Время 1: 20 пользователей одновременно нажимают "Забронировать"
         
         ┌─────────────────────────────────┐
         │  20 параллельных запросов       │
         │  POST /events/{id}/book         │
         └─────────────────────────────────┘
                      ↓
         ┌─────────────────────────────────┐
         │  lock (_bookingLock)            │
         │  Проверка и резервирование мест │
         └─────────────────────────────────┘
                      ↓
         ┌─────────────────────────────────┐
         │  5 успешных броней (Pending)    │
         │  15 ошибок 409 Conflict         │
         └─────────────────────────────────┘

Время 2: BackgroundService начинает обработку
         ┌─────────────────────────────────┐
         │  SemaphoreSlim (1 поток)        │
         │  Обработка 5 броней по очереди  │
         └─────────────────────────────────┘
                      ↓
         ┌─────────────────────────────────┐
         │  Все 5 броней → Confirmed       │
         │  AvailableSeats = 0             │
         └─────────────────────────────────┘
```

Результат:

* 5 пользователей успешно забронировали места (статус Pending → Confirmed)

* 15 пользователей получили ошибку 409 Conflict с сообщением "Нет свободных мест на это событие"

* У всех 5 успешных броней уникальные идентификаторы

* Событие имеет 0 свободных мест (AvailableSeats = 0)

Защита от овербукинга обеспечивается за счет:

1. Атомарной операции резервирования мест через lock

2. Проверки доступных мест перед созданием каждой брони

3. Синхронизации фоновой обработки через SemaphoreSlim
